## Цель и исходные требования

Разворачивать CLI-агентов Claude Code и Codex на сервере в серверном контуре.
Предусмотреть подключение других агентов без переписывания общей установки.
Сотрудник запускает развёртывание и подключается с Windows либо Ubuntu;
предпочтительна единая точка запуска для обеих ОС.

На сервере изначально есть только IP и root-аккаунт; SSH-ключи ещё не созданы.
Первоначальный вход — root по выданному паролю через SSH.
Физического доступа нет; доступ только по SSH, наличие консоли не предполагается.
Целевой способ подключения — по SSH-ключу.
Для повседневной работы создать непривилегированного пользователя.
Агент запускается в tmux и продолжает работать при отключении SSH.
Нужны доступ к выбранным файлам компьютера сотрудника и доступ через WireGuard
к серверам внутренних репозиториев.

Уточнения пользователя:

- Один сервер закреплён за одним человеком.
- Сервер: Ubuntu Server 24 (точный релиз проверить), 4–8 ГБ RAM, 2–4 CPU.
- WireGuard работает на сервере; через него доступны некоторые внутренние
  репозитории, другие находятся на GitHub. Нужны получение и отправка изменений.
- Авторизация агентов — личная подписка сотрудника.
- Нужны оба режима: прямой доступ к локальным папкам и синхронизация.
- Желательна автоматическая синхронизация при добавлении нового каталога,
  с предупреждением, если передача займёт больше примерно двух минут.
  Скорость каналов различается; учитывать в том числе канал 100 Мбит/с.
- Пилот проводится на Codex. Пользователь должен лично подключиться к сессии
  агента на сервере; установка без такого подключения не завершает пилот.

Все значимые действия фиксируются в журнале: цель, команда или операция,
результат, проверка и способ восстановления. По проверенным шагам формируется
ручная инструкция на случай отказа автоматизации. Секреты в журнал не попадают.

Сначала обсуждаем и согласуем план; настройка сервера и реализация скриптов — затем.

## Предлагаемая архитектура

```text
Компьютер сотрудника (Windows / Ubuntu)
  Python 3 + OpenSSH + единый launcher
       | SSH по ключу; передача выбранных файлов
       v
Выделенный одному сотруднику Linux-сервер (Ubuntu Server 24)
  личная Linux-учётная запись сотрудника
    личные настройки и авторизация агентов
    рабочие копии проектов
    tmux -> Claude Code / Codex / другой агент
       | внутренние маршруты через серверный WireGuard
       v
Внутренние репозитории и сервисы

Linux-сервер -> разрешённый интернет / прокси -> API поставщика модели
```

Серверное размещение CLI само по себе не означает локального исполнения модели.
До установки проверить допустимость передачи исходников и других рабочих данных
поставщику, нужный способ подключения и доступные корпоративные настройки.

### Учётные записи и SSH

Первичная подготовка доступа с нуля:

1. На компьютере сотрудника проверить наличие OpenSSH и сгенерировать отдельную
   пару Ed25519 для этого сервера. Не перезаписывать существующие ключи.
   Приватный ключ остаётся на компьютере; парольную фразу вводит сотрудник,
   при необходимости ключ загружается в локальный ssh-agent.
2. Получить IP и SSH-порт. Первоначальный вход root выполнить по выданному
   паролю через SSH. При ошибке входа остановиться с диагностикой;
   доступ к физической или провайдерской консоли не является частью сценария.
   Пароль вводится интерактивно и не сохраняется в конфиге или журнале.
3. Сверить отпечаток SSH-хоста с доверенным источником, установить публичный ключ
   в root authorized_keys, сохранив существующее содержимое и выставив права.
4. Отдельным SSH-соединением проверить вход root именно по созданному ключу,
   без отката на пароль. Парольный доступ сохраняется; при ручном выполнении
   первоначальную сессию оставить открытой до проверки.
5. Создать рабочего пользователя, установить ему публичный ключ сотрудника
   и проверить отдельный вход по ключу. Для root и рабочего пользователя допустим
   один клиентский ключ этого сервера; отдельный административный ключ — опция.
6. После проверки рабочего и административного доступа согласовать ограничения
   root-входа и паролей. Рабочий пользователь не становится единственным способом
   входа при отсутствии у него административных прав: сохранить управляемый
   административный доступ root по ключу. Отключение парольного входа — отдельный
   шаг после проверки ключей. Изменения sshd, firewall и маршрутов, способные
   прервать единственный доступ, требуют предварительной проверки конфигурации,
   резервной копии и запланированного на сервере автоматического отката;
   откат отменяется только после успешного нового подключения.
7. Серверные ключи для Git и WireGuard генерируются отдельно на сервере
   в соответствующих шагах; клиентский приватный SSH-ключ туда не переносится.

- Один рабочий непривилегированный пользователь на персональном сервере.
  Оба агента сотрудника могут работать в этой учётной записи.
- Root используется для первоначального provisioning. Рабочим агентам не выдаётся
  неограниченный sudo. Администрирование отделяется от запуска агентов.
- Проверка отпечатка SSH-сервера, прав каталогов и входа новым пользователем
  предшествует изменению действующего административного доступа.
- Для Git использовать отдельные учётные данные с необходимыми правами.
  Постоянный SSH agent forwarding по умолчанию не требуется.
- Для пилота достаточно выделенного сервера и непривилегированного пользователя.
  Учитывать бюджет RAM и диска при копировании файлов и запуске инструментов проекта.

### Файлы компьютера сотрудника: оба режима

1. **Синхронизация:** рабочая копия на сервере; обмен
   выбранной папкой или файлами с компьютером. Один источник истины для каждой
   операции; предварительный просмотр перезаписи, сохранение локальных изменений
   и остановка при конфликте. Одновременное редактирование не разрешается
   автоматической двусторонней перезаписью. Для репозиториев — отдельные клоны
   и обмен через Git; незакоммиченные файлы передаются отдельно по необходимости.
   Автосинхронизация — предлагаемая опция добавления каталога, а не безусловная
   зеркальная перезапись. Направление и правила конфликтов задаются при подключении.
2. **Прямой доступ:** отдельный канал к явно выбранным локальным папкам.
   Перед реализацией выбрать и проверить механизм для Windows и Ubuntu:
   ограниченный SFTP с обратным SSH-туннелем либо файловый мост.
   Начать с чтения, запись включать явно для выбранных папок.
   Предлагаемая для проверки схема: локальный ограниченный SFTP-сервис,
   обратный SSH-туннель и серверный файловый доступ через него. Сервис не требует
   публичного входящего порта на компьютере. Реализацию и зависимости выбрать
   после проверки Windows и Ubuntu; не предполагать, что Windows OpenSSH Server
   уже установлен. Туннель и доступ к папке должны иметь собственную авторизацию.

Для обоих режимов применяется одна явная привязка «локальная папка — серверный
путь». Live-доступ и синхронизированная копия публикуются разными путями:
сотрудник и агент должны понимать, где находятся актуальные данные. Нельзя
автоматически подменять исчезнувший live-каталог устаревшей копией.

Предлагаемое поведение при добавлении каталога:

1. Получить список файлов, их размеры и применённые исключения. Проверить
   свободное место на сервере. Время сканирования показывать отдельно.
2. До полной передачи оценить длительность: объём / измеренная полезная скорость
   плюс накладные расходы множества файлов. Если измерения ещё нет, показать
   предварительную оценку с явным предположением о скорости и уточнить её по
   небольшой ограниченной передаче с согласия пользователя.
3. При оценке более 120 секунд предупредить и предложить: продолжить в фоне,
   исключить тяжёлые каталоги, выбрать только прямой доступ или отменить.
   Для небольшой передачи автозапуск возможен после включения опции автосинхронизации.
4. Показать прогресс, оставшееся время и возможность прервать/возобновить передачу.
   Отмечать, когда первичная копия готова, и обнаруживать изменения во время копирования.
5. Для последующих изменений использовать инкрементальную передачу. Удаления
   и конфликтующие изменения не распространять молча. Служебное состояние Git,
   ключи, сокеты и зависимости проекта обрабатывать отдельной политикой.

Иллюстрация для канала 100 Мбит/с: теоретический предел — 12,5 МБ/с,
примерно 1,5 ГБ за 120 секунд без накладных расходов. Это не гарантированная
скорость: полезная скорость SSH, дисков и множества небольших файлов может
быть существенно ниже. Порог предупреждения определяется временем, а не
одним фиксированным размером папки для всех подключений.

При отключении компьютера прямой доступ к его файлам исчезает, хотя процесс агента
в tmux сохраняется. Автономная работа продолжается только с доступными серверу
ресурсами. Задача, зависящая от компьютера, должна явно остановиться или сообщить
о недоступности. Доступ к локальным файлам не означает возможность запускать
Windows-программы с Linux-сервера: это отдельное требование, если оно необходимо.

### WireGuard и сетевой доступ

- WireGuard размещается на сервере. Пользователь предоставит готовый конфиг
  позднее; сейчас файла нет. Предусмотреть --wg-config с локальным путём.
  При отсутствии файла подготовка Codex продолжается без активации VPN;
  внутренние репозитории проверяются после импорта конфигурации.
- VPN на компьютере сам по себе не даёт серверному агенту доступ к внутренней сети.
- Уточнить endpoint, выдачу peer, внутренние подсети, DNS, AllowedIPs и маршруты.
  Проверить отсутствие пересечения подсетей и сохранение административного SSH.
- По умолчанию предложены только необходимые внутренние маршруты; полный туннель
  выбирать лишь при требовании сети. Не превращать сервер в общий VPN-шлюз автоматически.
- Приватный ключ генерируется на соответствующем узле. В общий репозиторий
  передаются примеры без секретов, а не действующий конфиг с ключом.
- Проверить доступ к внутреннему Git через VPN и к GitHub через нужный внешний
  маршрут. Доступ к репозиториям должен поддерживать fetch/clone и push.
- Ключ входа сотрудника на сервер и Git-ключ сервера — разные назначения.
  Предложение: отдельный Git-ключ на сервере с правами личной учётной записи
  сотрудника; регистрацию публичного ключа и проверку прав согласовать по сервисам.
  Не предполагать, что один deploy key разрешает запись во все репозитории.

### Единая автоматизация

Предложение: Python 3 как переносимый launcher, системный OpenSSH как транспорт,
отдельные Linux-шаги на сервере. Один интерфейс не требует одного монолитного файла.
Python и SSH — явные зависимости; их установка на исходно пустой Windows
потребует небольшого отдельного шага или платформенных оболочек.

Параметры подключения будущего launcher:

- `--host` — обязательный адрес сервера;
- `--port` — необязательный SSH-порт, по умолчанию `22` без дополнительного вопроса;
  если задан, проверить целое число в диапазоне 1–65535;
- `--identity` — путь к ключу; для первого запуска ключ создаётся отдельным шагом;
- выбранный порт применяется ко всем SSH-соединениям, передаче файлов, туннелям
  и проверкам, включая повторное подключение к tmux.

Примеры предполагаемого интерфейса (скрипт ещё не реализован):

```text
python srv.py enroll --host SERVER_IP
python srv.py enroll --host SERVER_IP --port 2222
```

Предлагаемые операции будущего интерфейса:

- `doctor` — предварительная диагностика без изменений;
- `keygen` — создание локального SSH-ключа без перезаписи существующих;
- `enroll` — первоначальная установка публичного ключа через SSH с root-паролем,
  затем проверка входа по ключу;
- `bootstrap` — подготовка сервера администратором;
- `user add` — персональная учётная запись и публичный SSH-ключ;
- `agent install claude|codex` — установка выбранного агента;
- `connect` — новая сессия либо подключение к существующей tmux-сессии;
- `files` — подключение папок или явная передача файлов в выбранном режиме;
- `verify` — проверка результата и краткий отчёт;
- `update` — управляемое обновление с сохранением проверенной версии для отката.

Реализация должна учитывать повторный запуск и частичный отказ: сохранять прогресс,
не перезаписывать чужие настройки, делать резервные копии изменяемых конфигов,
показывать следующий ручной шаг. Изменения SSH, firewall и маршрутов выполнять
с проверкой нового соединения и восстановлением при неудаче.

Установка программ автоматизируется. Персональный интерактивный OAuth-вход
сотрудника может потребовать браузера; автоматизация должна провести через этот
шаг, а не обещать полностью безучастную авторизацию.

## Условия готовности

- Windows и Ubuntu используют один интерфейс запуска с описанными зависимостями.
- Каждый сотрудник подключается по своему ключу и работает без root.
- Один сервер обслуживает одного сотрудника; пилот соответствует Ubuntu Server 24,
  4–8 ГБ RAM и 2–4 CPU. Точный релиз, архитектуру и диск проверить диагностикой.
- Пользователь лично подключился к серверной сессии Codex с личной подпиской
  и выполнил короткое задание; после разрыва SSH вернулся в ту же сессию.
- Claude Code и Codex устанавливаются по выбору и запускаются в личной tmux-сессии.
- Разрыв SSH не завершает работающего агента; повторное подключение возвращает
  сотрудника в ту же сессию. Проверена политика завершения процессов при logout.
- Перезагрузка сервера рассматривается отдельно: tmux не сохраняет живой процесс
  после reboot. Документируется возобновление средствами соответствующего агента.
- Доступ к нужным репозиториям и выбранным локальным файлам соответствует
  утверждённой сетевой схеме; ограничения при отключении компьютера описаны.
- С сервера доступны fetch/clone и push для внутреннего Git через WireGuard
  и GitHub. Проверка реальной записи проводится в предназначенной для этого
  ветке/репозитории, без изменения рабочих веток по умолчанию.
- Прямой доступ и синхронизация проверены отдельно. При добавлении каталога
  передача дольше примерно двух минут сопровождается предупреждением;
  оценка учитывает канал и объём, а не только фиксированный порог в гигабайтах.
- Повторная установка и частичный отказ не уничтожают рабочие данные и конфигурацию.
- Ручная инструкция позволяет пройти те же операции без launcher; журнал содержит
  фактически выполненные команды и результаты без ключей, токенов и паролей.

## Открытые вопросы

1. Адрес пилотного сервера получен и записан в STATUS.md; порт стандартный, `22`.
   Первичный root-пароль выдаётся, сотрудник вводит его
   интерактивно при SSH-подключении. Отпечаток хоста получить из доверенного
   источника, если он доступен; иначе явно обозначить доверие при первом соединении
   и сохранить ключ хоста без отключения его дальнейшей проверки. Локальный ключ создаётся
   на первом шаге, его наличие от сотрудника заранее не требуется.
2. Точный релиз Ubuntu 24, архитектура, свободный диск (проверить на сервере).
3. Пользователь предоставит готовый WireGuard-конфиг. Получить локальный путь
   к нему, проверить маршруты и DNS без вывода приватного ключа. Активация
   выполняется с проверкой сохранения SSH и автоматическим откатом.
4. Есть ли доступ к OpenAI/Anthropic, нужен ли прокси и корпоративный CA?
5. Адреса репозиториев для пилота, способ личной Git-авторизации и место безопасной
   проверки push; кто зарегистрирует публичный Git-ключ сервера?
6. Папка для первого файлового сценария, права чтения/записи, направление
   автоматической синхронизации, исключения и политика удаления/конфликтов?
7. Допустимы ли Python 3 и OpenSSH как зависимости на клиенте? Нужны ли
   возобновление после reboot и резервные копии рабочих каталогов?
